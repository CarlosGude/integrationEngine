# agent.txt — Knowledge brief on IntegrationEngine

Purpose: a cold-start briefing for another AI agent/session picking up this
project. It summarizes what the bundle is, how it's built, its current
state, and non-obvious history/decisions that aren't visible just from
reading the code. For exhaustive architecture detail, defer to CLAUDE.md
(repo root) and docs/ — this file is the "why/context" layer on top.

## What this is

`carlosgude/integration-engine` — a Symfony bundle that enforces a
predictable, standardized structure for integrating external APIs. Every
integration endpoint is split into exactly two responsibilities: Request
(what goes in) and Response (what comes out), bridged by a Mapper that
turns the raw HTTP response into a typed DTO.

Origin: it did NOT start from a speculative design. It was extracted from
real pain on a production integration (a fashion/retail SaaS's Shopify
integration, "POF") where ad-hoc HTTP clients had become inconsistent and
hard to maintain. The project is deliberately closed to speculative
features and open only to needs proven by real usage. Two real consuming
contexts exist: the Shopify integration at POF, and a demo app built
during development (TMDB integration, webhooks demo).

Author: Carlos Gude (carlos.sgude@gmail.com) — senior architect. This is
simultaneously an open-source project and a marketing vehicle: there's a
12-week content plan (Dev.to + LinkedIn articles, problem-first framing,
the bundle as the "consequence" not the pitch) and a Cloudflare-Worker
landing page under `landing/` with its own CLAUDE.md and a persona-based
review standard (architect/middle/CTO/junior/CEO scored 1–100, floor 75).

## Current state (as of 2026-10-14)

- Latest tag: **v9.2.0**. Recent trajectory: v9.0.0 (breaking: URL
  placeholders resolve exclusively from context, never body — see
  ADR 0016/CHANGELOG), v9.1.0 (breaking: body passed to send()/sendMany()
  must match the class declared in YAML `body:`, enforced before the HTTP
  call), v9.2.0 (opt-in `profiler_payloads` option — shows action
  body/context/response in the Symfony Profiler panel, debug-only, never
  headers/credentials/failed-response content; ADR 0019).
- 119 test files under `tests/`. Suite structure: `tests/Core/` (engine
  contract, path resolution, dynamic auth incl. 401 retry, connection
  resolution, mapper invariant), `tests/Infrastructure/` (HTTP adapter,
  request middleware, GraphQL, PSR-6 cache, adapter resolver),
  `tests/Bundle/` (DI extension, compiler pass, generator, make:integration),
  `tests/Fake/` (hand-written fakes, no mocks on internal methods).
- Quality gates: `make ci` = cs + stan (phpstan level max) + test +
  deptrac (architecture layers) + infection (mutation testing). Mutation
  Covered-Code MSI gate is 90% (lowered from an unreachable 95% in
  v8.0.1 after measuring real coverage at 92.46%).
- 19 ADRs in `docs/adr/` — read these for *why*, not just CHANGELOG for
  *what*. Recent ones: 0016 generic webhooks + app-owned idempotency,
  0017 PHPStan contracts, 0018 body-type invariant, 0019 profiler payload
  visibility.
- `docs/ROADMAP.md` explicitly separates shipped vs. proposed; a feature
  only counts as current once implementation + tests + wiring exist in
  the repo — plans/spikes live under `docs/archived/` once stale.
- Out of scope by design (per ROADMAP): vendor-specific integrations
  inside the bundle, a plugin registry, bundle-owned business workflows,
  a second Messenger/DLQ abstraction, webhook exactly-once guarantees,
  application IAM/credential persistence, deployment-specific metric
  storage.

## Architecture — condensed (full detail in CLAUDE.md)

Data flow: `IntegrationRegistry::get(NAME)` → `IntegrationEngine::send()`
→ `ConfigPort` loads the YAML-declared Action → optional
`ConnectionResolverInterface` resolves per-tenant baseUrl/auth → optional
dynamic-auth token fetch/cache → `MiddlewareClient` (CachingMiddleware →
user middlewares → TracingMiddleware[debug] → HTTP adapter) → adapter
resolves path/body into a `Request`, runs `RequestMiddlewareInterface`
chain, makes the transport call → `AbstractMapper::map()` → typed
`ResponseInterface` DTO. Application services must translate these DTOs
to domain objects; DTOs must never leak into the domain.

Three built-in client adapters (rest/graphql/form_encoded), pluggable via
tagged `integration_engine.client_adapter`. Batch support
(`sendMany`/`sendManyOrFail`) runs concurrently when the client implements
`BatchClientInterface`, falling back to sequential when request
middlewares are configured (they need to observe/short-circuit per-item,
e.g. OAuth 1.0a signing) or when the client lacks batch capability.

Key invariant enforced at runtime: every `AbstractMapper` must declare
`getAction(): string` matching its paired action; mismatches throw.

## Non-obvious history / decisions worth knowing before touching code

- **Breaking changes are frequent and intentional** — this is a fast-
  moving pre-1.0-in-spirit bundle (despite major version 9) that doesn't
  shy from v-major breaks when the old behavior was a footgun (body-as-
  path-param resolution, implicit body typing). Check CHANGELOG.md and
  the matching `docs/UPGRADE-X.0.md` before assuming backward compat.
- **Resilience boundary was relitigated**: a decision to move resilience
  (retry/circuit-breaker) "outside the engine" was later reverted in
  v8.0.0 — see ADR 0015 and `src/Core/Resilience` /
  `src/Compatibility/Resilience`. If you see resilience code, don't
  assume it's dead weight from an abandoned direction; check ADR 0015
  dates vs. current code before removing anything.
- **Security**: the Symfony Profiler is treated as a secret-leak surface.
  Multiple fixes (v8.0.4, v9.2.0 ADR 0019) specifically ensured it never
  persists exception messages, headers, credentials, or failed-response
  bodies — only safe scalars (class names, status codes). Any profiler-
  facing feature needs the same paranoia.
- **Mutation testing's 100% MSI can be misleading** — high Infection MSI
  has previously masked under-covered classes; don't trust it blindly,
  manually check which classes/branches are actually exercised by tests.
- **CI has gone red on `main` before** (e.g. around 2026-09-23, due to an
  unreachable mutation gate) — if CI is red, check whether it's a real
  regression or a stale/miscalibrated gate before chasing a phantom bug.
- **Demo app** (used for TMDB + webhooks integration testing) has had
  recurring friction: a client-model break in v7.0 (per-integration
  clients, not global) required manual service registration as a
  stopgap; its test kernel is known to hang >60s locally — rely on CI,
  not local runs, for that suite.
- **`.claude/` and `.codex/` are tracked in git** (not gitignored) as of
  the last audit — intentional, not an accident, if you see them in
  `git status`.
- **Landing page (`landing/`) is a separate Cloudflare Worker app** with
  its own stack (html.js/css.js/client.js/i18n en+es) and its own
  CLAUDE.md. It is not part of the PHP bundle's runtime or CI gates and
  has an explicit, scored review process — don't apply bundle PHP
  conventions to it, and don't skip the persona review when asked to
  touch copy.

## Workflow / collaboration notes

- Carlos writes marketing articles himself; an assistant's job is to
  polish text he supplies, never to generate full articles from scratch
  — avoid any "AI slop" framing or structure he didn't originate.
- No new feature proposals unless asked — the bundle is explicitly in a
  "marketing / consolidation" phase, not a "grow scope" phase. Stick to
  real bugs and explicitly requested work.
- Always show a proposed commit message and wait for confirmation before
  running `git commit` (Carlos commits on his own otherwise, but expects
  the assistant to check first).
- For code review requests, a persona-based pass (senior/middle/junior,
  each scored for confidence/quality) is the preferred structure; exact
  output format/threshold still to be nailed down with him.
